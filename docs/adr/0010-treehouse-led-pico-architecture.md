# ADR 0010 — TreeHouse LED driver: two MicroPython Picos with PIO

**Status:** Accepted

## Context

The TreeHouse drives 8 SK6812 RGBW LED channels across 7 named displays (dioramas, Forge & Flora arc/bloom, Dormer, Porch Lights, Attic TV & Lamps). All hardware — Raspberry Pi and microcontrollers — lives in the garage (the open tech bay at the base of the structure). Wire runs radiate from there to display locations throughout the house.

The RP2040 has 8 PIO state machines (2 blocks × 4). Driving SK6812 strips simultaneously requires one PIO state machine per channel. With 8 channels, one Pico is at full PIO capacity with zero headroom.

The branch controller already occupies `/dev/ttyACM1` (ADR-0005). Linux enumerates `/dev/ttyACMx` in plug order, which is not stable across reboots.

## Decision

### Two Picos

Use two Pi Picos, split by functional group:

**Pico A — "dioramas"** (`/dev/treehouse-pico-a`): House Swarming (pin 0), Club (pin 1), Mycelium (pin 2), Forge & Flora arc (pin 3), Forge & Flora bloom (pin 4). Five channels.

**Pico B — "structure"** (`/dev/treehouse-pico-b`): Dormer (pin 0), Porch Lights (pin 1), Attic TV & Lamps (pin 2). Three channels.

Each Pico uses 3–5 of its 8 PIO state machines, leaving headroom for future strips.

### MicroPython + PIO firmware

Both Picos run the same MicroPython firmware. PIO state machines handle the timing-critical SK6812 signal; MicroPython handles JSON parsing and USB serial I/O. The Raspberry Pi is the animation engine — the Pico firmware is a dumb pixel sink.

### Protocol unchanged

The existing JSON-lines-over-USB-serial protocol from `pico_driver.py` is preserved:

```
{"pin": <int>, "pixels": [[r, g, b, w], ...]}\n
```

Fire-and-forget at 30 fps. No acknowledgement. The Pi instantiates one `PicoDriver` per Pico.

### Stable device names via udev

Three USB serial devices (Pico A, Pico B, branch controller) get stable symlinks via udev rules keyed on USB serial number:

```
/dev/treehouse-pico-a    → Pico A (dioramas)
/dev/treehouse-pico-b    → Pico B (structure)
/dev/treehouse-branches  → branch controller
```

Udev rules are generated by `scripts/install-services.sh` using serial numbers recorded in `network.json`. `settings.json` references stable names, never `/dev/ttyACMx`.

### Forge & Flora: two channels

Forge & Flora uses two independent SK6812 channels (arc on pin 3, bloom on pin 4 of Pico A) rather than one blended channel. The `ForgeAndFloraDisplay` class computes per-channel pixel arrays separately; `get_pixels()` returns two `ChannelFrame` objects. Arc LED count and bloom LED count are independently configurable in `settings.json` (`arc_led_count`, `bloom_led_count`).

## Reasons

- Two Picos gives fault isolation: a Pico A failure kills dioramas but not Porch Lights or Dormer; a Pico B failure kills structure lights but not dioramas.
- Each Pico stays well under PIO capacity — room for future strips without hardware swap.
- MicroPython + PIO: PIO handles the timing-sensitive SK6812 protocol; MicroPython handles the application logic (JSON parsing). No GC-induced timing glitch risk on the signal line.
- MicroPython preferred over Arduino here (unlike the branch controller) because the LED Pico has no Dynamixel or OSC dependency — simpler language is the right tool.
- Stable udev symlinks prevent plug-order-dependent `/dev/ttyACMx` assignment, which is a recurring source of field failures.

## Consequences

- `PicoDriver` must be instantiated twice in `main.py`, one per Pico.
- `settings.json` splits `"pico"` into `"pico_dioramas"` and `"pico_structure"`. `main.py` must route each display's `ChannelFrame` objects to the correct driver.
- `ForgeAndFloraDisplay.get_pixels()` returns two `ChannelFrame` objects (arc + bloom) instead of one.
- `install.sh` must write udev rules and record each Pico's USB serial number during first deploy.
- Firmware (`Firmware/TreeHouse_PicoLEDs/main.py`) is the same file flashed to both Picos — no per-Pico firmware differentiation.
